# vendored

A `vpc` node sourced from a git address rather than a local path. See [docs/vendoring.md](../../docs/vendoring.md) for the concept. Unlike the other examples, `blueprint.hcl`, `vendor/vpc/`, and `vendor.yaml` here are **committed as real, already-vendored output** (not regenerated on demand) because that's what vendoring is for: `vendor/vpc/` holds only `main.tf`/`outputs.tf`, no `README.md`, because `vendor.yaml`'s `exclude: ["*.md"]` pruned it, which you can see recorded right there in the manifest entry. Clone and run directly, no setup needed:

```
cd examples/vendored
go run ../../cmd/terragraph validate
go run ../../cmd/terragraph apply --auto-approve
```

`blueprint.hcl`'s `source` is a `git::file:///abs/path/...?ref=v1.0.0` address rather than an `https://...` one. That's not the recommended form for a real project; it's what makes *this specific example* self-contained: `upstream/` is a throwaway git repo committed nowhere (gitignored, regenerated by `setup.sh`), so the example has something to point at without depending on a real external repository staying available forever. A real project's `blueprint.hcl` just names the actual upstream, e.g. `git::https://github.com/terraform-aws-modules/terraform-aws-vpc.git?ref=v5.1.0`.

`setup.sh` is not part of the clone-and-run flow above. It exists only if you want to watch `terragraph vendor` actually *fetch* something instead of just reading the committed result. It rebuilds `upstream/` and overwrites `blueprint.hcl` to point at *your* machine's local path, so after running it `git diff` will show `blueprint.hcl` changed. `git checkout blueprint.hcl` restores the committed version once you're done:

```
cd examples/vendored
./setup.sh
go run ../../cmd/terragraph vendor --force
cat vendor.yaml   # source now reflects the fresh (local) address
git checkout blueprint.hcl   # restore the committed version when done
```
